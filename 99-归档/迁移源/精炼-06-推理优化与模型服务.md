# 推理优化与模型服务（精炼）

> 定位：理解 Decoder-only LLM 从 prompt 到逐 token 输出的运行方式，以及 KV Cache、MQA/GQA、PagedAttention 为什么直接影响吞吐、延迟和显存。

## 自回归生成

语言模型每一步根据已有上下文预测一个新 token：

```text
上下文
→ forward
→ 取最后位置 logits
→ Softmax/采样或贪心选择
→ 拼接新 token
→ 再次 forward
```

第 $t$ 步需要 $p(x_t\mid x_{<t})$，所以生成天然具有串行依赖。batch 内可以并行，但同一序列的下一个 token 必须等待当前 token 产生。

## Prefill 与 Decode

| 阶段 | 输入 | KV Cache | 常见特征 |
| --- | --- | --- | --- |
| Prefill | 整个 prompt，通常多个 token | 计算并建立所有层的历史 K/V | 并行度高，通常更偏计算密集 |
| Decode | 每条活跃序列一个新 token | 读取历史 K/V，并追加本步 K/V | 串行迭代，通常更受显存带宽和调度影响 |

Prefill 决定首 token 前的主要工作；Decode 决定持续生成速度。两阶段的输入形态和瓶颈不同，不能只用一个“每 token 延迟”概括。

## KV Cache 的机制

Attention 为每个 token、每层产生 Q/K/V。生成新 token 时：

- 新 Q 只用于当前这一步查询，因此通常不需要长期保存。
- 历史 K 会被后续所有 Q 用于计算匹配分数。
- 历史 V 会被后续注意力权重加权汇总。

因此缓存历史 K/V：

```text
Prefill：计算 prompt 的 K/V → 写入缓存
Decode：只计算新 token 的 Q/K/V
        新 Q × 所有历史 K → 权重
        权重 × 所有历史 V → 当前输出
        将新 K/V 追加到缓存
```

KV Cache 避免每步重复计算历史 token 的 K/V 投影和隐藏状态，但不会消除当前 Q 对全部历史 K/V 的读取与注意力计算。上下文越长，单步 Decode 仍会变慢。

## 计算复杂度直觉

- 对长度 $t$ 的整段序列重新执行普通 Attention，单头注意力矩阵计算约为 $O(t^2d_h)$，所有头合计约为 $O(t^2D)$。
- 若每生成一步都从头重算整个增长序列，重复生成的累计注意力工作会非常昂贵。
- 使用 KV Cache 后，每个新 token 只产生一行注意力分数，对历史长度近似线性增长；累计生成仍随总长度呈二次增长，而不是常数成本。
- 实际耗时还包括 Q/K/V 投影、FFN、kernel 启动、batch 调度和内存读写，不能只凭大 O 直接推断真实性能。

## KV Cache 显存

设：

- `B`：并发序列数；
- `L`：层数；
- `T`：缓存序列长度；
- `H_kv`：K/V 头数；
- `d_h`：每头维度；
- `s`：每个元素的字节数。

忽略对齐和管理开销，缓存大小近似：

$$
M_{KV}\approx 2BLTH_{kv}d_hs
$$

系数 2 来自 K 和 V。MHA 中通常 $H_{kv}=H_q$；MQA 中 $H_{kv}=1$；GQA 位于两者之间。因此长上下文、高并发和多层模型会迅速放大缓存占用。

原材料中用 $2LTD$ 估算的 32 层、4096 token、hidden size 4096、FP16 示例约为 2 GiB，它隐含了 batch size 为 1 且 $H_{kv}d_h=D$。对 GQA/MQA 必须使用实际 K/V 头数，不能继续直接套 hidden size。

## MQA、GQA 与缓存

```text
MHA：每个 Query head 有独立 K/V
MQA：所有 Query heads 共享一组 K/V
GQA：每组 Query heads 共享一组 K/V
```

减少 `H_kv` 会近似同比减少 KV Cache 和 Decode 时的 K/V 读取量。代价是 K/V 表达共享增加，可能影响质量，因此 GQA 常作为折中。它们改变的是注意力头组织，不是把 KV Cache 完全取消。

## PagedAttention

不同请求的长度、结束时间和增长速度不同，若为每条序列预留连续的大块 KV 内存，会产生预留浪费和碎片。

PagedAttention 将 KV Cache 切成固定大小的块，并通过逻辑块到物理块的映射进行管理：

- 物理内存不必连续；
- 缓存可按需增长和回收；
- 更容易组织不同长度请求和连续批处理；
- 减少碎片与过度预留，提高可承载并发。

它主要优化 KV Cache 的内存管理与调度，不改变 Attention 数学公式，也不会自动减少每个 token 必须保存的 K/V 元素数。

## 训练与推理的区别

- 训练可一次并行处理整段 `[B,T]`，需要保存激活供反向传播，并对所有位置计算 loss。
- 推理不反传，但自回归 Decode 串行，并需要长期保留历史 K/V。
- 常规全序列训练一般不使用推理式 KV Cache，因为所有位置并行计算且参数持续更新；训练保存的是反向传播所需激活，目标与 KV Cache 不同。
- `model.eval()` 与 `no_grad()` 能关闭特定训练行为和计算图，但不会自动启用 KV Cache；Cache 必须由模型接口和推理引擎显式支持。

## 易错点

- KV Cache 是以“每层”为单位保存，不只是保存输入 embedding 或最后一层结果。
- 缓存 K/V 不代表 Attention 变成 $O(1)$；当前 Q 仍需读取历史。
- Prefill 也会建立 KV Cache，不是只有 Decode 才使用缓存。
- Decode “通常受内存带宽限制”是经验描述，会随模型、batch、硬件和上下文长度变化。
- PagedAttention 解决内存分配和批处理问题，不等同于 FlashAttention；后者主要优化 Attention 计算的 IO 路径。
- 生成代码中简单拼接全部 `idx` 并重新 forward，不代表已实现 KV Cache。
