# 大模型常见概念

## 1. 基础概念

### 1.1 LLM（大语言模型）

#### 核心定义

LLM（Large Language Model，大语言模型）是利用大规模文本数据训练、能够处理和生成自然语言的模型。它通常接收一段 Token 序列，并预测后续 Token 的概率分布。

#### 深度解析

现代 LLM 多以 Transformer 为基础，通过预训练学习语言规律、事实关联、常见推理模式和任务形式。模型参数保存的是从训练数据中压缩得到的统计规律，而不是可以逐条查询的知识库。对话模型通常还会经过 SFT、偏好优化等后训练，使其更能遵循指令。

#### 机制与实例

用户输入“解释什么是注意力机制”后，文本先被 Tokenizer 转成 Token，模型结合上下文逐步预测输出 Token，最终形成回答。模型每一步本质上仍是在条件概率下选择后续内容。

#### 关联概念

LLM 是模型本身；Agent 是围绕模型加入工具、记忆和执行循环形成的系统。RAG 为 LLM 临时提供外部资料，Fine-Tuning 则会改变模型参数。

### 1.2 Token

#### 核心定义

Token 是语言模型读取和生成文本时使用的基本单位。它可能是一个汉字、单词、子词、标点或字节片段，并不固定等于自然语言中的“一个词”。

#### 深度解析

模型不能直接处理原始字符串，Tokenizer 会先把文本切分成 Token，再映射为数字编号。Token 的划分取决于具体模型的分词方案，因此同一句话在不同模型中可能得到不同数量的 Token。模型的输入长度、输出长度和使用成本通常都以 Token 计算。

#### 机制与实例

英文单词 unfamiliar 可能被拆成多个子词，中文短语“大语言模型”可能按单字或常见词片段切分。模型生成回答时也是每次产生一个或若干 Token，而不是一次生成整句话。

#### 关联概念

Tokenizer 负责 Token 与文本之间的转换；Context Window 限制一次请求可容纳的 Token 总量；Embedding 将离散的 Token 编号转换为连续向量。

### 1.3 Tokenizer（分词器）

#### 核心定义

Tokenizer 是在文本与 Token 序列之间进行转换的组件，通常包含切分规则、Token 到编号的映射，以及必要的特殊标记处理。

#### 深度解析

编码时，Tokenizer 将字符串转换为 Token ID；解码时，再把 Token ID 还原为可读文本。常见方案会使用子词或字节级切分，以在词表规模和未知文本处理能力之间取得平衡。Tokenizer 通常与模型训练时的词表绑定，不能随意替换。

#### 机制与实例

输入“你好，LLM！”后，Tokenizer 会按自身规则生成一串 Token ID。模型只接收这些编号及相关掩码，输出的编号再由同一个 Tokenizer 解码为文本。

#### 关联概念

Token 是切分后的单位，Tokenizer 是执行切分与映射的组件。预训练模型与 Tokenizer 必须匹配；Context Window 统计的也是 Token 数量，而不是字符数。

### 1.4 Context（上下文）

#### 核心定义

Context 是模型在当前一次推理中能够参考的信息集合，包括系统指令、历史消息、当前问题、外部文档、工具结果以及其他被放入输入的信息。

#### 深度解析

模型生成每个 Token 时，会依据当前上下文计算条件概率。上下文不是模型参数中的长期知识，也不天然跨会话保存；新会话是否能利用旧信息，取决于应用是否重新提供历史内容或使用记忆机制。上下文质量会直接影响回答的相关性和一致性。

#### 机制与实例

连续对话中，用户说“把上一段改短”，模型需要在 Context 中看到“上一段”才能理解指代。如果应用没有把上一轮内容传入，模型就无法仅凭这句话可靠地完成任务。

#### 关联概念

Context 是实际提供给模型的信息，Context Window 是它能容纳信息的容量上限。Prompt 是构造 Context 的重要部分，Agent Memory 则负责在需要时把历史信息重新放入 Context。

### 1.5 Context Window（上下文窗口）

#### 核心定义

Context Window 是模型单次处理 Token 的容量限制。它通常需要容纳输入消息、附加资料、工具结果、系统指令以及模型将要生成的内容。

#### 深度解析

上下文窗口越大，模型一次可参考的材料越多，但并不代表它能同等准确地利用窗口中的每个细节。长上下文还会增加计算、延迟和成本。不同模型或服务对输入与最大输出的计算方式可能不同，应以具体接口说明为准。

#### 机制与实例

当一段长文档与对话历史之和接近容量上限时，应用可能需要删除旧消息、压缩摘要或只检索相关片段，否则请求可能超限，或留给回答的空间不足。

#### 关联概念

Context Window 是容量边界，Context 是窗口里实际存在的内容。RAG、摘要和 Agent Memory 都可用于控制进入窗口的信息，但不能消除模型本身的长度限制。

### 1.6 Prompt（提示词）

#### 核心定义

Prompt 是提供给模型、用于说明任务并引导输出的输入内容。它可以包含指令、背景、示例、约束、数据和期望的输出格式。

#### 深度解析

有效 Prompt 通常会明确目标、上下文、边界和验收要求。Prompt 不只指用户最后一句话；在对话系统中，它往往由 System Prompt、历史消息、User Prompt、工具信息等共同构成。Prompt 可以影响行为，但不能保证模型绝不出错。

#### 机制与实例

“总结这篇文章”是一个宽泛 Prompt；加入“面向初学者、列出三点、不得补充原文没有的事实”后，任务边界更清楚，输出也更容易检查。

#### 关联概念

User Prompt 表达用户当前需求，System Prompt 设置整体规则。Prompt 被放入 Context，Chain of Thought、Few-shot 示例和结构化输出要求都属于提示策略。

### 1.7 User Prompt（用户提示词）

#### 核心定义

User Prompt 是由最终用户提交的请求或消息，用于表达当前任务、问题、材料和期望结果。

#### 深度解析

User Prompt 是模型输入的一部分，但不是唯一指令来源。应用通常还会加入 System Prompt、开发者配置、工具描述和历史消息。若用户请求与更高优先级的系统规则冲突，系统规则通常优先；具体优先级由模型接口和应用设计决定。

#### 机制与实例

用户输入“读取这份表格并找出异常值”属于 User Prompt。应用会同时提供表格内容、可用工具和安全约束，模型再综合这些信息决定如何处理。

#### 关联概念

User Prompt 面向当前请求，System Prompt 面向整个会话或应用行为。两者都会进入 Context，并共同影响模型输出。

### 1.8 System Prompt（系统提示词）

#### 核心定义

System Prompt 是应用提供给模型的高层指令，用来设定角色、行为边界、输出原则、工具使用规则和安全要求。

#### 深度解析

它通常由系统开发者配置，而不是普通用户直接编写。System Prompt 可以约束模型如何响应 User Prompt，例如指定语言、要求引用来源或禁止执行某些操作。但它仍是一种输入指令，不等同于绝对安全隔离，重要权限还需要由应用和运行环境控制。

#### 机制与实例

客服系统可以用 System Prompt 要求“仅依据公司政策回答，信息不足时说明无法确认”。用户提出问题后，模型会在该总体规则下组织回答。

#### 关联概念

System Prompt 与 User Prompt 都属于 Prompt。前者提供长期规则，后者提供当前任务；工具权限、沙箱和访问控制则属于系统层保障，不能只靠提示词实现。

### 1.9 Embedding（嵌入）

#### 核心定义

Embedding 是把 Token、文本或其他对象映射为连续数值向量的表示方式，使模型或检索系统可以在向量空间中处理它们。

#### 深度解析

在 LLM 内部，Token ID 会先变成向量，再进入 Transformer。独立的 Embedding Model 还可把句子或文档映射为向量，用于语义检索、聚类和相似度计算。向量距离通常反映训练目标下的相关性，但不保证事实一致或逻辑等价。

#### 机制与实例

RAG 系统把用户问题和文档片段分别编码为向量，再搜索距离较近的片段。检索结果随后作为上下文交给 LLM 生成答案。

#### 关联概念

Tokenizer 产生离散 Token ID，Embedding 将其变成连续表示。Vector Database 存储和检索向量，Reranker 可对初步召回结果进一步排序。

### 1.10 Transformer

#### 核心定义

Transformer 是以注意力机制为核心的神经网络架构，广泛用于语言模型、视觉模型和多模态模型。

#### 深度解析

它通常由注意力层、前馈网络、残差连接和归一化等模块组成。注意力允许序列中不同位置相互聚合信息，训练时也便于并行处理。许多生成式 LLM 使用仅解码器结构，并通过因果掩码保证当前位置只能利用允许看到的前文。

#### 机制与实例

处理“银行旁边的河岸”时，模型可通过上下文中其他 Token 的关系更新“银行”的表示，从而区分金融机构与河岸等含义。多个 Transformer 层会逐步形成更丰富的表示。

#### 关联概念

Attention 是 Transformer 的核心模块之一，但 Transformer 还包括前馈网络、残差连接等结构。LLM 常以 Transformer 为基础，Embedding 为其提供输入表示。

### 1.11 Attention（注意力）

#### 核心定义

Attention 是一种根据当前查询与其他位置的相关程度，对信息进行加权聚合的机制。

#### 深度解析

常见做法是把输入变换为 Query、Key 和 Value，利用 Query 与 Key 计算权重，再对 Value 加权求和。多头注意力让模型在不同表示子空间中并行学习关系。注意力权重有助于观察信息流，但不能简单等同于模型完整的解释过程。

#### 机制与实例

在“这本书虽然很长，但它很有趣”中，处理“它”时，注意力机制可以聚合“书”等相关位置的信息，使当前表示包含指代关系。

#### 关联概念

Transformer 使用 Attention 建模序列关系；KV Cache 会保存推理过程中已经计算的 Key 和 Value；Context Window 决定可参与注意力计算的上下文范围。

### 1.12 Chain of Thought（CoT，思维链）

#### 核心定义

Chain of Thought 是让模型在给出结论前生成若干中间推理步骤的提示或训练方式，常用于数学、逻辑和多步任务。

#### 深度解析

中间步骤可以帮助模型分解问题，也便于用户检查部分过程。CoT 可以通过示例提示、明确要求或后训练获得，但更长的推理并不必然更正确。模型输出的思维链也不一定忠实反映其全部内部计算，因此不能把它当作完全可靠的解释。

#### 机制与实例

解决多步应用题时，模型先列出已知量、计算中间结果，再给出答案。若某个步骤出错，后续结论仍可能错误，因此还需要规则校验或外部工具。

#### 关联概念

CoT 是推理表达方式，不等同于 Transformer 的内部机制。Agent 可把任务分解与工具调用组织成外部执行轨迹，Verifier 或 Eval 用于检查结果。

### 1.13 Hallucination（幻觉）

#### 核心定义

Hallucination 指模型生成了流畅但缺乏事实依据、与提供材料冲突或无法被可靠验证的内容。

#### 深度解析

LLM 的训练目标通常是预测合理的后续 Token，而不是直接查询权威事实，因此在信息不足、问题含糊或要求超出知识范围时仍可能生成看似可信的答案。幻觉不是模型有意欺骗，也不能仅靠扩大模型或提示词完全消除。

#### 机制与实例

用户询问一篇并不存在的论文时，模型可能组合出合理的标题、作者和摘要。使用检索、工具、引用核验和“不确定时明确说明”可以降低风险。

#### 关联概念

RAG 可提供外部证据，Tool 可查询实时数据，Evaluation 和 Bad Case 分析可测量错误模式；这些方法只能降低幻觉，不能保证所有输出都正确。

### 1.14 GLM（General Language Model）

#### 核心定义

GLM 在大模型语境中通常指基于自回归空白填充目标提出的一类语言模型预训练框架，也常用于指代由该技术路线发展出的模型系列。

#### 深度解析

原始 GLM 通过遮盖连续文本片段，再按自回归方式重建缺失内容，并引入二维位置编码等设计，以统一理解、条件生成和无条件生成任务。后续具体模型可能采用不同架构和训练方案，因此不能把所有名称中带 GLM 的模型都简化为原始论文实现。

#### 机制与实例

训练时，句子中的一段内容被替换为空白标记，模型在看到其余上下文后逐步生成缺失片段。通过改变空白数量和长度，可以构造不同类型的训练任务。

#### 关联概念

GLM 是特定预训练框架或模型系列名称，LLM 是更宽泛的类别。它也不要与统计学中的 Generalized Linear Model（广义线性模型）混淆。

## 2. 训练与对齐

### 2.1 Pre-training（预训练）

#### 核心定义

Pre-training 是在大规模通用或领域数据上训练模型，使其获得语言建模、知识表示和通用能力的初始阶段。

#### 深度解析

生成式 LLM 常使用下一 Token 预测作为训练目标，从大量未人工逐条标注的文本中学习。预训练通常消耗最多的计算资源，得到的 Base Model 能续写文本，但未必稳定遵循用户指令。后续可通过 SFT 和偏好优化改善交互行为。

#### 机制与实例

给定“机器学习是一种”，模型预测后续 Token，并根据真实文本计算损失、更新参数。重复处理海量序列后，模型逐渐学习语言结构和内容关联。

#### 关联概念

Pre-training 产生基座模型；Fine-Tuning 在此基础上针对任务继续训练；SFT 和 DPO 都属于常见后训练方法。

### 2.2 Fine-Tuning（微调）

#### 核心定义

Fine-Tuning 是在已训练模型的基础上，使用新的数据和目标继续更新参数，使模型适应特定任务、领域或行为要求。

#### 深度解析

微调可以更新全部参数，也可以只训练少量新增参数。它可能用于分类、领域适配、指令遵循或偏好对齐。微调效果取决于数据质量、训练目标和评测设计，并非数据越多或训练越久越好；不当微调还可能损害原有能力。

#### 机制与实例

将通用模型用一批客服问答数据继续训练后，它可能更熟悉业务术语和回答格式。是否真正改善仍需在独立评测集上比较微调前后的表现。

#### 关联概念

SFT 是带有标准答案的监督微调；LoRA 是参数高效微调方法；DPO 使用偏好对微调模型行为。

### 2.3 SFT（Supervised Fine-Tuning，监督微调）

#### 核心定义

SFT 是使用人工编写或筛选的输入—目标输出样例，对预训练模型进行监督学习的后训练方法。

#### 深度解析

训练时，模型通常学习在给定指令和上下文后生成目标回答，并通过交叉熵损失提高目标 Token 的概率。SFT 可以让模型掌握对话格式、任务模式和基本指令遵循，但它主要模仿数据中的答案，未直接表达多个答案之间的偏好强弱。

#### 机制与实例

数据包含“用户问题—理想回答”对。模型读取问题后预测回答 Token，与目标答案比较并更新参数。训练完成后，需要在未参与训练的任务上评测是否提升。

#### 关联概念

Instruction Tuning 通常通过多任务指令数据进行 SFT。Preference Data、DPO 和 RLHF 常在 SFT 模型基础上进一步优化偏好。

### 2.4 Instruction Tuning（指令微调）

#### 核心定义

Instruction Tuning 是用覆盖多种任务的自然语言指令与示范答案训练模型，使其更善于理解和执行人类指令。

#### 深度解析

它通常采用 SFT 目标，但强调数据由“指令—输入—输出”形式组织，并覆盖不同任务表达。其目的不是只学会某个固定任务，而是提高模型面对新指令时的迁移能力。指令质量、多样性和格式一致性会影响结果。

#### 机制与实例

训练集中同时包含摘要、改写、分类、问答和格式转换等指令。模型学习到不同指令对应不同输出行为，之后可尝试处理未完全相同的新任务。

#### 关联概念

Instruction Tuning 是 SFT 的常见应用形式；System Prompt 是推理时指令，不更新参数；Alignment 还可能使用 DPO、RLHF 等偏好方法。

### 2.5 LoRA（Low-Rank Adaptation）

#### 核心定义

LoRA 是一种参数高效微调方法：冻结大部分原模型参数，在部分线性层旁加入可训练的低秩矩阵，用较少参数表示权重更新。

#### 深度解析

它降低了训练时需要更新和保存的参数量，使同一基座模型可以挂载多个轻量适配器。LoRA 减少的是可训练参数及相关优化器状态，不代表基座模型本身不占显存，也不保证在所有任务上等同于全参数微调。

#### 机制与实例

微调一个大模型时，只训练注意力层中的 LoRA 矩阵。训练结果保存为较小的适配器文件，推理时可与原模型共同加载或合并到权重中。

#### 关联概念

LoRA 属于 PEFT 和 Fine-Tuning；QLoRA 在量化后的基座模型上训练 LoRA；Quantization 本身则是降低数值精度的技术。

### 2.6 QLoRA（Quantized Low-Rank Adaptation）

#### 核心定义

QLoRA 是在低精度量化的基座模型上训练 LoRA 适配器的参数高效微调方法，目标是进一步降低微调所需显存。

#### 深度解析

训练过程中，量化后的基座权重通常保持冻结，计算时按需要转换到合适精度，而 LoRA 参数继续以可训练精度更新。QLoRA 让有限显存环境能够微调更大的模型，但仍需关注量化误差、序列长度、激活和优化器状态。

#### 机制与实例

将基座权重以较低位宽加载，再在目标层加入 LoRA。训练只保存适配器参数，不需要为全部原始权重维护梯度和优化器状态。

#### 关联概念

QLoRA = 量化基座模型 + LoRA 微调。它不同于只为部署加速而做的推理量化，也不等同于全参数低精度训练。

### 2.7 Preference Data（偏好数据）

#### 核心定义

Preference Data 是描述人类或评判系统更偏好哪个输出的数据，常见形式是在同一 Prompt 下提供 chosen 与 rejected 两个回答。

#### 深度解析

偏好可以来自人工比较、规则、模型评判或可验证奖励。高质量偏好数据需要明确评价标准，并控制长度、风格和格式等混杂因素，否则模型可能学到表面特征而非目标能力。偏好数据既可用于训练 Reward Model，也可直接用于 DPO。

#### 机制与实例

对同一道题生成两个回答，标注者依据正确性和指令遵循选择较好的一个。记录 Prompt、chosen、rejected 及必要元数据，形成训练样例。

#### 关联概念

SFT 数据给出单个目标答案，Preference Data 表达答案之间的相对关系。Reward Model、DPO 和部分 RLHF 流程都会使用它。

### 2.8 Reward Model（奖励模型）

#### 核心定义

Reward Model 是对候选输出给出标量分数或偏好判断的模型，用于近似人类或任务定义中的质量标准。

#### 深度解析

它常通过偏好数据训练，使 chosen 的得分高于 rejected。奖励模型可以为强化学习提供反馈，也可用于候选排序和评测。但其分数只是所学偏好的近似，可能受训练数据偏差、分布外输入和奖励投机影响。

#### 机制与实例

给定同一问题的多个回答，Reward Model 分别打分，策略模型通过强化学习倾向产生高分回答。实际使用中还需要人工抽查或客观指标校准奖励是否可信。

#### 关联概念

经典 RLHF 流程通常显式训练 Reward Model；DPO 直接利用偏好对，不要求单独部署奖励模型；LLM-as-a-Judge 可承担评判工作，但不一定经过奖励建模训练。

### 2.9 RLHF（Reinforcement Learning from Human Feedback）

#### 核心定义

RLHF 是利用人类反馈构造学习信号，再通过强化学习优化模型行为的一类方法。

#### 深度解析

典型流程包括 SFT、收集人类偏好、训练 Reward Model，以及使用 PPO 等算法优化策略模型。人类反馈使目标不必完全写成程序规则，但流程复杂，且奖励模型可能不能准确代表真实偏好。不同系统的具体 RLHF 实现并不完全相同。

#### 机制与实例

模型对同一 Prompt 生成多个回答，人类进行排序；排序用于训练奖励模型；策略模型随后生成回答并依据奖励更新，使输出更符合偏好。

#### 关联概念

Reward Model 提供奖励信号，SFT 常作为起点。DPO 使用偏好数据直接优化策略，不属于“显式奖励模型 + 在线强化学习”的经典实现。

### 2.10 DPO（Direct Preference Optimization）

#### 核心定义

DPO 是直接使用偏好对优化语言模型的后训练方法，使模型提高 chosen 回答的相对概率并降低 rejected 回答的相对概率。

#### 深度解析

DPO 从受约束的奖励最大化问题推导出分类式目标，通常比较当前策略与参考模型对偏好回答的概率。它不需要显式训练 Reward Model，也不需要在训练过程中进行在线采样和 PPO 更新，因此工程上相对简洁，但仍依赖可靠偏好数据和合适超参数。

#### 机制与实例

输入同一个 Prompt 的 chosen 与 rejected 回答，计算两者在当前模型和参考模型下的相对对数概率，再更新当前模型，使 chosen 更占优势。

#### 关联概念

DPO 通常从 SFT 检查点开始，使用 Preference Data。它与经典 RLHF 追求相似的偏好对齐目标，但优化形式和训练流程不同。

### 2.11 GRPO（Group Relative Policy Optimization）

#### 核心定义

GRPO 是一种策略优化方法，通过比较同一问题下成组采样结果的相对奖励来估计优势，并更新语言模型策略。

#### 深度解析

它源自 PPO 类方法，但可利用组内奖励统计替代单独的价值模型，从而减少一部分训练资源。GRPO 常用于具有规则验证器或可计算奖励的推理任务。它仍需要生成多个候选、计算奖励并进行策略更新，复杂度通常高于离线 DPO。

#### 机制与实例

对一道数学题采样多条解答，用答案校验器评分；每条结果相对于组内平均表现得到优势，模型据此提高高奖励轨迹的概率。

#### 关联概念

GRPO 属于强化学习式后训练；DPO 主要基于离线偏好对；Reward Model、规则或 Verifier 都可能为 GRPO 提供奖励。

### 2.12 Alignment（对齐）

#### 核心定义

Alignment 是使模型行为更符合预期目标、人类偏好、安全边界和使用规范的过程与研究方向。

#### 深度解析

对齐不仅是让回答“更友好”，还包括指令遵循、真实性、有用性、安全性和可控性等目标。不同目标之间可能冲突，对齐标准也会随场景变化。SFT、RLHF、DPO、规则约束和系统安全控制都可参与对齐，但没有单一方法能保证完整对齐。

#### 机制与实例

一个基座模型先通过 SFT 学习回答格式，再用偏好数据减少不相关输出，同时在系统层加入权限控制和内容策略。最终还需通过独立 Eval 验证。

#### 关联概念

SFT 和 DPO 是模型层对齐方法；System Prompt 是推理时约束；安全策略、Tool 权限和人工审核属于系统层措施。

### 2.13 Knowledge Distillation（知识蒸馏）

#### 核心定义

Knowledge Distillation 是让较小的学生模型学习较强教师模型输出、分布或中间表示，以转移能力的训练方法。

#### 深度解析

教师可以生成软标签、解释过程或合成数据，学生模型再据此训练。蒸馏可能降低部署成本并保留部分能力，但学生受模型容量、数据覆盖和教师错误限制，也可能继承教师的偏差与幻觉。

#### 机制与实例

教师模型为大量问题生成答案和推理示例，经过筛选后用于 SFT 学生模型。随后比较学生在任务指标、速度和成本上的变化。

#### 关联概念

蒸馏改变学生模型参数；Quantization 改变数值表示；二者都可用于压缩，但机制不同。Synthetic Data 常作为蒸馏载体。

### 2.14 Quantization（量化）

#### 核心定义

Quantization 是用更低精度的数值格式表示模型权重或激活，以减少存储、显存占用和部分计算成本。

#### 深度解析

常见做法包括训练后量化和量化感知训练。较低位宽通常能提高部署效率，但可能造成精度损失，实际收益还取决于硬件、算子支持和推理框架。量化不是简单压缩文件，必须结合任务质量与真实延迟评测。

#### 机制与实例

将浮点权重映射到较低位宽表示，在支持相应算子的设备上推理。部署前比较量化前后的准确率、生成质量、显存与吞吐。

#### 关联概念

QLoRA 使用量化基座来降低微调显存；Knowledge Distillation 通过教师—学生训练压缩能力；KV Cache 量化则针对推理期间的缓存。

## 3. 推理与评测

### 3.1 Inference（模型推理）

#### 核心定义

Inference 是使用已经训练好的模型处理输入并产生预测或生成结果的过程，通常不再更新模型参数。

#### 深度解析

对生成式 LLM 而言，推理包含输入处理、模型前向计算和逐 Token 解码。它与训练的主要区别是没有反向传播和优化器更新，但仍会消耗显存和计算资源。模型“推理”这个工程术语也不等同于逻辑推理能力；简单文本生成同样属于 Inference。

#### 机制与实例

用户发送问题后，系统编码输入，模型先处理已有上下文，再逐步生成输出 Token，直到遇到停止条件。服务会记录延迟、吞吐和资源占用。

#### 关联概念

Temperature、Top-k 和 Top-p 控制解码；KV Cache 减少重复计算；Quantization 可降低部分推理成本。

### 3.2 Temperature

#### 核心定义

Temperature 是生成时调整候选 Token 概率分布平滑程度的参数，用于影响输出的随机性和多样性。

#### 深度解析

模型先产生 Logits，Temperature 通常在 Softmax 前对它们进行缩放。较低值会放大高概率 Token 的优势，使输出更集中；较高值会让分布更平缓，增加低概率 Token 被采样的机会。它不直接提高模型知识或正确率，极端设置还可能使输出僵化或不稳定。

#### 机制与实例

生成事实型答案时可使用较低 Temperature 以减少随机变化；创意写作可适当提高。相同 Prompt 在非确定性采样下可能得到不同结果。

#### 关联概念

Temperature 调整整个概率分布，Top-k 和 Top-p 则限制候选集合。三者常组合使用，但具体效果依赖模型和服务实现。

### 3.3 Top-k

#### 核心定义

Top-k 是一种采样策略：每一步只保留概率最高的 k 个候选 Token，再从这些候选中采样。

#### 深度解析

它通过固定候选数量排除大量低概率 Token，可以减少异常输出，同时保留一定多样性。k 较小会使结果更保守，k 较大则更接近从完整分布采样。由于不同生成位置的概率分布形状不同，固定 k 不一定总能保留同等概率质量。

#### 机制与实例

若 k=5，模型在某一步只从概率最高的五个 Token 中选择，其他 Token 即使概率非零也不会被采样。

#### 关联概念

Top-k 固定候选数量；Top-p 按累计概率动态选择候选；Temperature 调整候选之间的相对概率。

### 3.4 Top-p

#### 核心定义

Top-p 又称 Nucleus Sampling（核采样），每一步保留累计概率达到阈值 p 的最小候选集合，再从中采样。

#### 深度解析

当模型对少数 Token 很有把握时，候选集合会较小；分布较平坦时，候选集合会自动扩大。因此 Top-p 相比固定 Top-k 更能适应不同位置的不确定性。p 越低通常越保守，越高则允许更多长尾候选。

#### 机制与实例

若最高概率的几个 Token 累计达到 0.9，设置 p=0.9 时只在这些 Token 中采样，而不要求候选数量固定。

#### 关联概念

Top-p 与 Top-k 都用于截断采样分布，常与 Temperature 配合。它们改变生成策略，但不能修复模型本身的知识缺口。

### 3.5 KV Cache

#### 核心定义

KV Cache 是自回归生成时保存历史 Token 在注意力层中 Key 和 Value 计算结果的缓存机制。

#### 深度解析

生成新 Token 时，历史部分的 Key 和 Value 通常不必重复计算，模型只需计算新位置并与缓存交互，从而降低逐步解码的重复工作。缓存大小会随层数、序列长度、批量大小和表示维度增长，长上下文或高并发时可能占用大量显存。

#### 机制与实例

模型已经生成 100 个 Token 后，第 101 步复用前 100 个位置的 KV Cache，而不是重新计算整个前缀的全部 Key 和 Value。

#### 关联概念

KV Cache 用于 Inference 的自回归解码，训练时通常一次并行处理整段序列，不以同样方式使用缓存。Quantization 和推理系统可进一步优化缓存占用。

### 3.6 Evaluation / Eval（评测）

#### 核心定义

Evaluation 是用明确任务、数据和指标测量模型或系统表现的过程，简称 Eval。

#### 深度解析

可信 Eval 需要定义评测目标、数据边界、解码配置和计分方式，并保证不同模型在可比条件下测试。评测可包含自动指标、规则检查、模型裁判和人工抽查。单一分数通常无法覆盖真实性、安全性、成本和不同样例分布。

#### 机制与实例

在固定测试集上比较 Base Model、SFT Model 和 DPO Model，统一 Prompt 模板和生成参数，记录主指标、资源消耗以及失败样例。

#### 关联概念

Benchmark 提供标准化任务或数据；LLM-as-a-Judge 是一种评判方式；Bad Case 是对具体失败样例的进一步分析。

### 3.7 Benchmark（基准测试）

#### 核心定义

Benchmark 是为了可重复比较模型能力而设计的一组任务、数据、指标和评测规则。

#### 深度解析

它通常针对知识、推理、代码、指令遵循等能力提供统一入口。Benchmark 分数便于横向比较，但可能受到数据污染、提示模板、解码设置和任务代表性影响。公开榜单表现不必然等同于真实业务效果。

#### 机制与实例

多个模型在同一数学题集合上使用相同答案抽取和准确率规则评测，得到可比较结果。项目仍需补充符合自身场景的评测集。

#### 关联概念

Benchmark 是标准化评测载体，Evaluation 是更广泛的评测过程。Harness 可统一执行任务、模型适配和指标计算。

### 3.8 LLM-as-a-Judge（大模型裁判）

#### 核心定义

LLM-as-a-Judge 是使用一个语言模型依据给定标准，对其他模型的回答进行评分、分类或成对比较的评测方法。

#### 深度解析

它适合难以用精确规则衡量的开放式质量，如完整性、风格或帮助程度。裁判模型可能存在位置偏差、长度偏好、自我偏好和提示敏感性，因此需要清楚的评分标准、顺序交换、一致性检查及人工抽查。它不是天然客观的“真值”。

#### 机制与实例

把问题、评价标准和两个匿名回答交给裁判模型，请其选择更好回答并给出理由；交换回答顺序再次评测，检查结果是否稳定。

#### 关联概念

LLM-as-a-Judge 可用于 Evaluation 或构造 Preference Data。Reward Model 通常是经过专门偏好训练的评分模型，二者用途可能重合但并不等同。

### 3.9 Bad Case（失败样例）

#### 核心定义

Bad Case 是模型或系统未达到预期的具体样例，包括答案错误、指令违背、格式失败、工具误用或成本异常等情况。

#### 深度解析

Bad Case 分析不应只收集“答错了”，而要记录输入、模型版本、配置、期望、实际输出和可能原因，并按稳定标准分类。单个失败不能直接证明普遍问题，但一组有规律的失败可用于定位数据、模型、Prompt、检索或评测缺陷。

#### 机制与实例

评测中发现模型经常忽略多重约束，便将样例按“遗漏约束、误解约束、输出格式错误”分类，再针对性构造 SFT 或偏好数据。

#### 关联概念

Evaluation 发现 Bad Case，Bad Case 分析推动数据和方法迭代。Benchmark 给出总体可比结果，而 Bad Case 提供更细的失败证据。

## 4. Agent 与工具

### 4.1 Agent（智能体）

#### 核心定义

Agent 是围绕模型建立的目标驱动系统，它能够获取上下文、决定下一步、调用工具、观察结果并持续执行，直到完成任务或触发停止条件。

#### 深度解析

LLM 常充当决策核心，但完整 Agent 还需要执行循环、工具、状态管理、权限和错误处理。自主程度可以从“每步需人工确认”到“在边界内连续执行”不等。并非所有聊天机器人都是 Agent，也不是加入一次 Function Calling 就自动具备可靠自治能力。

#### 机制与实例

代码 Agent 接到“修复测试失败”后，先运行测试、读取报错、查找代码、修改文件，再次运行测试并汇报结果。每次工具结果都会进入后续决策。

#### 关联概念

LLM 提供推理与生成，Agent Harness 提供执行环境，Tool 提供行动能力，Agent Memory 保存或检索跨步骤信息。

### 4.2 Tool（工具）

#### 核心定义

Tool 是提供给模型或 Agent 的可调用能力，用于读取外部信息、执行计算或改变外部系统状态。

#### 深度解析

工具通常具有名称、用途说明、输入参数和返回结果。底层可以是函数、API、数据库、命令行程序或浏览器操作。模型负责决定是否调用并生成参数，宿主应用负责权限检查和实际执行；有副作用的工具应设置确认和访问边界。

#### 机制与实例

天气工具接收城市和日期，调用外部服务后返回结构化天气数据。模型根据结果生成回答，而不是凭参数记忆猜测实时天气。

#### 关联概念

Function Calling 描述结构化调用形式，Tool Calling 描述选择和调用工具的过程。MCP 可以标准化工具的发现与连接，但 Tool 不一定通过 MCP 提供。

### 4.3 Tool Calling（工具调用）

#### 核心定义

Tool Calling 是模型或 Agent 选择某个工具、生成调用参数、接收执行结果并继续处理的完整过程。

#### 深度解析

典型流程包括工具注册、模型选择、参数校验、宿主执行、结果回传和后续响应。模型产生调用意图不代表工具已经执行，真正的副作用由应用程序完成。可靠系统还需要处理超时、权限拒绝、错误返回和重复调用。

#### 机制与实例

用户要求查询订单，模型选择订单工具并填入订单号；应用验证用户权限后调用后端，把查询结果返回给模型，模型再组织解释。

#### 关联概念

Tool 是能力本身，Tool Calling 是一次调用流程。Function Calling 是常见的结构化接口机制，Agent 会把多次调用组织进执行循环。

### 4.4 Function Calling（函数调用）

#### 核心定义

Function Calling 是让模型按照预先声明的函数名称和参数结构，输出机器可解析调用请求的机制。

#### 深度解析

开发者通常提供函数描述和参数 Schema，模型根据对话生成函数名与参数。应用解析、验证并执行函数，再把结果交还模型。Function Calling 主要解决自然语言到结构化调用的映射，不负责自动授权，也不保证参数一定正确。

#### 机制与实例

函数定义要求 city 为字符串、date 为日期。模型面对天气问题输出相应结构化参数，应用校验后调用真实天气服务。

#### 关联概念

Function Calling 可用于实现 Tool Calling。Tool 的范围更广，可代表浏览器、命令行等能力；MCP 在协议层定义工具发现和调用接口。

### 4.5 Agent Skill（智能体技能）

#### 核心定义

Agent Skill 是为某类重复任务封装的可复用能力包，通常包含触发说明、操作步骤、领域规则，以及可选的脚本、模板和参考资料。

#### 深度解析

Skill 侧重“如何完成一类任务”，它可以指导 Agent 组合多个工具和步骤，而不一定对应一个原子函数。好的 Skill 应有清楚的适用范围、输入输出和失败处理。不同 Agent 产品对 Skill 的文件格式和加载机制可能不同。

#### 机制与实例

“处理 PR 评审意见”Skill 可以规定先读取评论、区分已解决线程、修改代码、运行测试并汇报，而实际读取 GitHub 和执行测试分别由不同 Tool 完成。

#### 关联概念

Tool 提供单项行动能力，Agent Skill 提供可复用任务方法。Framework 或 Agent Harness 负责加载和执行 Skill，Workflow 可描述更高层业务过程。

### 4.6 Agent Memory（智能体记忆）

#### 核心定义

Agent Memory 是 Agent 保存、压缩、检索并在后续任务中重新使用信息的机制。

#### 深度解析

记忆可以是当前任务内的短期状态，也可以是跨会话保存的长期信息。实现方式包括对话历史、摘要、结构化数据库、文件或向量检索。保存信息不等于模型永久学会它；只有被检索并放入当前 Context 的内容才能直接影响本次推理。

#### 机制与实例

Agent 把项目构建命令和已确认的代码规范写入记忆。下次处理同一项目时，系统检索这些信息并加入上下文，减少重复探索。

#### 关联概念

Context 是本次可见信息，Context Window 是容量限制，Agent Memory 是跨步骤或跨会话管理信息的系统。RAG 可作为记忆检索的一种实现方式。

### 4.7 MCP（Model Context Protocol，模型上下文协议）

#### 核心定义

MCP 是连接 AI 应用与外部系统的开放标准，使应用能够通过统一协议发现和使用数据、工具及可复用提示。

#### 深度解析

MCP 采用 Host、Client、Server 的分工：Host 是承载模型的 AI 应用，通常为每个 Server 管理相应 Client；Server 暴露 Tools、Resources 和 Prompts 等能力。MCP 规定连接和上下文交换方式，但不规定模型如何推理，也不自动替代权限、安全和业务逻辑。

#### 机制与实例

编程 Agent 连接代码托管 MCP Server，先发现可用工具和资源，再读取问题信息或提交查询。Host 负责把返回内容交给模型，并控制是否允许执行有副作用的操作。

#### 关联概念

Tool 是可执行能力；MCP 是发现、连接和调用这些能力的一种标准方式。Function Calling 是模型生成结构化参数的机制，二者处于不同层次。

### 4.8 Multi-Agent（多智能体）

#### 核心定义

Multi-Agent 是由多个 Agent 分工、通信或协作完成任务的系统形式。

#### 深度解析

不同 Agent 可以承担规划、检索、编码、评审等角色，也可以并行处理彼此独立的子任务。多智能体并不天然优于单 Agent，它会增加通信成本、上下文损失、结果冲突和调度复杂度，只有任务可分解且协作收益明确时才有价值。

#### 机制与实例

主 Agent 拆分前端、后端和测试任务，三个 Agent 在隔离环境中工作，最后由主 Agent 汇总结果、解决冲突并统一验证。

#### 关联概念

Agent Harness 可提供子 Agent 创建和消息传递；Orchestration 决定分工顺序；Workflow 描述整体任务过程。

### 4.9 RAG（Retrieval-Augmented Generation，检索增强生成）

#### 核心定义

RAG 是在模型生成回答前，从外部数据源检索相关内容并放入 Context，以增强事实依据和领域信息的系统方法。

#### 深度解析

典型流程包括文档切分与索引、查询检索、可选重排、上下文构造和模型生成。RAG 可以更新知识而不重新训练模型，但结果取决于数据质量、召回、重排和生成约束。检索到资料也不保证模型一定正确引用或推断。

#### 机制与实例

企业问答系统将政策文档切分并建立索引。用户提问后，系统检索相关片段、重排并连同问题交给 LLM，再要求模型依据这些片段回答。

#### 关联概念

Embedding 和 Vector Database 常用于语义检索，Reranker 改善候选排序。RAG 改变输入 Context，Fine-Tuning 则改变模型参数。

### 4.10 Vector Database（向量数据库）

#### 核心定义

Vector Database 是面向高维向量存储、索引和相似度检索设计的数据系统。

#### 深度解析

它通常保存向量、原始内容标识和元数据，并使用近似最近邻索引快速查找相似项目。向量数据库解决的是检索效率与管理问题，语义质量主要由 Embedding Model、数据切分和过滤策略决定。普通数据库加向量扩展也能实现类似能力。

#### 机制与实例

文档片段被编码为向量并写入数据库。用户问题也被编码后，系统查询最相近的若干片段，再按权限和元数据过滤。

#### 关联概念

Embedding 产生向量，Vector Database 保存并检索向量，Reranker 对召回结果进一步排序，RAG 使用最终结果构造 Context。

### 4.11 Reranker（重排模型）

#### 核心定义

Reranker 是对检索系统初步召回的候选结果重新评分和排序的模型或算法。

#### 深度解析

第一阶段检索强调快速召回，Reranker 则使用更丰富的查询—文档交互来提高前几名结果的相关性。它通常只处理有限候选，因此可以使用计算更重的交叉编码器或 LLM。重排会增加延迟，必须结合最终任务效果评估收益。

#### 机制与实例

向量检索先返回 50 个文档片段，Reranker 逐一评估它们与问题的相关性，选出最合适的 5 个放入上下文。

#### 关联概念

Vector Database 负责高效召回，Reranker 提高排序质量，RAG 使用重排后的文档。两阶段职责不同，不能用重排完全替代召回。

### 4.12 Claude Code

#### 核心定义

Claude Code 是 Anthropic 提供的智能体编程工具，可理解代码库、编辑文件、运行命令并结合开发工具完成任务。

#### 深度解析

它不只是一种底层模型，也不再局限于终端界面；可通过终端、IDE、桌面端和网页等环境使用。其 Agent Harness 将 Claude 模型与文件操作、搜索、命令执行、上下文管理和权限控制结合起来，并可通过 Skills、MCP 等机制扩展。

#### 机制与实例

用户要求修复缺陷后，Claude Code 搜索项目、读取相关文件、执行测试、修改代码并再次验证。是否允许某些命令或外部访问由运行环境和用户权限决定。

#### 关联概念

Claude 是模型系列，Claude Code 是智能体编程产品。Agent Harness 描述其模型之外的运行支撑层，MCP 和 Agent Skill 是扩展能力的方式。

### 4.13 Codex

#### 核心定义

Codex 是 OpenAI 编程技术与产品名称。历史上它指面向自然语言到代码生成的模型；当前语境中通常也指能够理解代码库、修改文件、运行检查和协助交付的软件工程智能体。

#### 深度解析

当前 Codex 可在应用、命令行和云端等工作环境中承担代码理解、功能实现、缺陷修复和代码评审任务。它的能力来自模型与工具、上下文、沙箱、权限及工作流的组合，因此不能再只描述为“输出代码文本但无法执行”的被动模型。具体功能会随产品更新而变化。

#### 机制与实例

用户提交一个仓库任务后，Codex 可以定位相关代码、实施修改、运行测试并展示差异；涉及外部系统或高风险操作时，仍受权限和确认机制约束。

#### 关联概念

早期 Codex 模型与当前 Codex 产品共享名称但定位不同。当前 Codex 属于 Agentic Coding 系统，可使用 Tool、Skill、MCP 和 Agent Harness 等能力。

## 5. 工程组织

### 5.1 Harness（执行脚手架）

#### 核心定义

Harness 是包围核心模型或组件的运行支撑层，负责准备输入、连接能力、驱动执行、收集输出并实施必要控制。“执行脚手架”是便于理解的译法，实际语境也常称运行框架或支撑层。

#### 深度解析

在大模型系统中，Harness 可能管理 Prompt、Context、Tool、重试、权限、日志和评测。它本身不等同于模型，也不一定是完整通用 Framework；其重点是让核心能力能够在受控环境中实际运行和验证。同一模型在不同 Harness 中可能表现出明显差异。

#### 机制与实例

评测 Harness 读取任务样例，适配不同模型接口，统一生成参数，执行请求、解析答案并计算指标，从而减少手工比较的不一致。

#### 关联概念

Agent Harness 专门支撑 Agent 循环；Framework 提供更广泛的复用结构；Pipeline 和 Workflow 描述过程组织。

### 5.2 Agent Harness（智能体运行脚手架）

#### 核心定义

Agent Harness 是把模型转化为可运行 Agent 的支撑层，通常提供工具、上下文管理、执行循环、状态、权限和结果验证。

#### 深度解析

模型负责理解与决策，Harness 负责把决策连接到真实环境并把观察结果送回模型。它还可能处理最大步数、超时、重试、沙箱和人工确认。Agent 表现不只取决于模型，工具设计和 Harness 的控制逻辑同样重要。

#### 机制与实例

编程 Agent Harness 向模型提供读文件、编辑和运行测试工具；模型选择动作后，Harness 校验权限、执行操作、返回结果，并决定是否继续下一轮。

#### 关联概念

Agent 是整体行为主体，Agent Harness 是运行支撑层。Agent Skill 提供任务方法，Tool 提供动作，Workflow 描述更高层目标流程。

### 5.3 Framework（框架）

#### 核心定义

Framework 是为一类应用提供可复用结构、组件、扩展点和控制流程的软件基础。

#### 深度解析

大模型 Framework 可能封装模型调用、Prompt、数据、Tool、Agent、评测或部署能力。开发者在框架规定的生命周期和接口内填充业务逻辑。框架可以提高开发效率，但也会带来抽象成本和依赖，不应以“使用某框架”替代对底层数据流和模型行为的理解。

#### 机制与实例

Agent Framework 提供工具注册、消息类型和执行器，开发者实现具体工具与任务规则，再由框架驱动运行。

#### 关联概念

Framework 是通用软件结构；Harness 更强调围绕核心组件的运行支撑；Pipeline、Workflow 可以在 Framework 内实现。

### 5.4 Pipeline（流水线）

#### 核心定义

Pipeline 是将数据或任务按一组相对明确的阶段依次处理，并把前一阶段输出交给后一阶段的组织方式。

#### 深度解析

Pipeline 强调数据流、阶段边界和可重复执行，通常适合顺序较稳定的处理过程。它可以包含分支或并行步骤，但整体仍以输入经过若干变换得到输出为中心。每个阶段应有明确输入、输出和失败处理，便于复现和定位问题。

#### 机制与实例

RAG Pipeline 可以表示为文档切分、Embedding、索引、检索、重排、Prompt 构造和生成。某阶段质量下降可沿数据流逐步排查。

#### 关联概念

Pipeline 偏技术数据流；Workflow 偏完整任务和业务协作；Framework 可提供实现 Pipeline 的组件。

### 5.5 Workflow（工作流）

#### 核心定义

Workflow 是为完成一个目标而组织的任务、角色、条件分支、人工决策和系统动作的整体流程。

#### 深度解析

它比 Pipeline 更关注“谁在什么条件下做什么”，可以包含等待、审批、回退、循环和跨系统协作，不要求所有步骤都是线性数据处理。LLM 或 Agent 可以参与某些环节，但 Workflow 的控制权也可以主要由确定性程序掌握。

#### 机制与实例

内容发布 Workflow 包括生成草稿、事实核查、人工审批、发布和异常回滚；其中生成由 LLM 完成，审批和发布由其他系统控制。

#### 关联概念

Pipeline 常作为 Workflow 中的技术子流程。Agent 可动态决定部分步骤，Framework 和 Harness 提供执行基础，Tool 完成具体动作。
